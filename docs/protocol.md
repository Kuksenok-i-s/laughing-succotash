# Gateway ↔ Agent Core protocol

Version: **1**

A single persistent WebSocket carries JSON-RPC 2.0 as a control plane and raw binary frames as a
data plane. Agent Core dials out to the Gateway, so the Mac mini needs no inbound listener and no
public address.

```
Agent Core (Mac mini)  ──outbound WSS──▶  Telegram Gateway (VPS)
```

Both peers may originate requests once the connection is up.

## 1. Connection

### 1.1 Handshake

Core connects to `wss://<gateway-host>/rpc` with:

```
Authorization: Bearer <CORE_TOKEN>
```

The Gateway compares the token in constant time and rejects with HTTP `401` before the WebSocket
upgrade if it does not match. The token never appears in logs. TLS is validated normally; there is
no mTLS and no VPN.

Immediately after upgrade the Core sends `core.hello`. Until the Gateway has replied to it, the
Gateway sends no requests other than the `core.hello` response, and rejects every other inbound
method with `-32001 not_ready`.

### 1.2 Keepalive

WebSocket ping every 20 s, pong deadline 20 s. A missed pong drops the connection and triggers the
Core's reconnect loop. This is a deliberately short window: a silently half-open TCP connection is
the most common failure mode on a residential uplink, and the Core must notice it quickly because
it is the only party that can re-dial.

### 1.3 Reconnect

Only the Core reconnects. Delay is `min(base * 2^attempt, max)` with full jitter:

```
delay = random_uniform(0, min(RECONNECT_BASE_DELAY * 2**attempt, RECONNECT_MAX_DELAY))
```

Defaults: base 1 s, max 60 s. The attempt counter resets after a connection has been healthy for
60 s, so flapping does not immediately reset backoff to zero.

## 2. Message framing

Text frames are JSON-RPC 2.0 objects, one per frame. Batches are not supported.

Binary frames carry upload payload and are described in §6.

## 3. Envelope conventions

Every method that changes state carries an idempotency key. All identifiers are ULID strings
(lexicographically sortable, generated by whichever side originates the object).

| Field | Owner | Meaning |
| --- | --- | --- |
| `request_id` | Gateway | One inbound Telegram interaction |
| `job_id` | Core | One unit of async work |
| `operation_id` | Core | One side-effecting tool invocation |
| `delivery_id` | Core | One outbound Telegram action |
| `event_id` | either | One durable event |
| `upload_id` | Core | One binary upload |
| `action_id` | Core | One pending confirmation |

Users are always namespaced strings — `"tg:123456789"` — never bare integers. This keeps the
identity space open for a future non-Telegram front end and makes an accidental integer collision
impossible.

Timestamps are RFC 3339 with explicit offset. Internally both sides use timezone-aware UTC.

## 4. Sequencing and delivery

Delivery is **at-least-once with idempotent application**. There is no attempt at exactly-once.

Each side maintains a monotonically increasing `seq` for the durable events it originates.
Durable events are persisted before being written to the socket.

- `core.hello.params.last_received_seq` — highest Gateway-originated seq the Core has durably applied.
- The `core.hello` result carries the Gateway's `last_received_seq` for Core-originated events.

After the handshake each side replays its unacknowledged events with `seq` greater than the peer's
reported value, in ascending order, before sending anything new. Acknowledgement is piggybacked:
every request carries an optional `ack_seq`, and `rpc.ack` exists for idle acknowledgement.

Receivers deduplicate on the natural key:

| Repeated | Must not |
| --- | --- |
| `delivery_id` | send a second Telegram message |
| `operation_id` | create a second reminder / event / task, or delete twice |
| `event_id` | be processed twice |
| `request_id` | start a second job |

A repeated request returns the **original** result. This makes blind retry after a lost response
safe, which is the whole point: the sender cannot distinguish "request lost" from "response lost".

## 5. Methods — Gateway → Core

### `core.hello`
Sent by Core (despite the direction of the rest of this group, this one is Core-originated; it is
listed here because it opens the session).

```json
{"instance_id":"home-macmini","protocol_version":1,"last_received_seq":1842,
 "capabilities":["assistant","audio","reminders","calendar","tasks","notes","memory"]}
```

Result:

```json
{"gateway_version":"1.0.0","protocol_version":1,"last_received_seq":907,
 "server_time":"2026-08-23T19:00:00+00:00"}
```

If `protocol_version` is unacceptable the Gateway responds `-32000 protocol_version_unsupported`
and closes with code `4400`. Version negotiation is strict equality for v1; a future v2 Core must
be able to speak v1 to an old Gateway.

### `assistant.submit`

```json
{"request_id":"01K...","user_id":"tg:123456789","chat_id":123456789,
 "message_id":4711,"kind":"text|command|transcribe_request",
 "text":"...","command":"/new",
 "reply_to":{"message_id":4700,"has_audio":true},
 "upload_id":"01K...",
 "client_time":"2026-08-23T19:00:00+03:00"}
```

Returns immediately — never blocks for the duration of the work:

```json
{"job_id":"01K...","status":"accepted","dedup":false}
```

`dedup: true` means this `request_id` was already accepted and the original `job_id` is returned.

### `audio.begin` / `audio.commit` / `audio.abort`
See §6.

### `job.cancel`
`{"job_id":"01K..."}` → `{"cancelled":true|false}`. `false` means the job had already finished.

### `confirmation.resolve`

```json
{"action_id":"01K...","user_id":"tg:123456789","choice":"approve|reject",
 "resolved_at":"2026-08-23T19:00:00+00:00"}
```

Result `{"status":"applied|already_resolved|expired|unknown"}`. Resolving the same `action_id`
twice is safe and returns `already_resolved` without re-running the action.

### `session.reset`
`{"user_id":"tg:123456789","request_id":"01K..."}` → `{"conversation_id":"01K..."}`. Backs `/new`.

### `status.get`
`{}` → aggregated health, rendered by `/status`:

```json
{"core":{"connected":true,"uptime_seconds":8123,"instance_id":"home-macmini"},
 "cursor":{"state":"ready","backend":"acp","version":"2026.08.11-e8db854"},
 "stt":{"state":"ready","model":"large-v3","device":"cpu"},
 "scheduler":{"state":"ready","pending_reminders":3,"next_trigger":"2026-08-23T20:00:00+00:00"},
 "jobs":{"running":1,"queued":2}}
```

Never includes credentials.

## 6. Audio upload

JSON-RPC is the control plane; bytes travel as binary frames. Base64 is not used — it would
inflate a 60-minute recording by a third and force it through the JSON parser.

### 6.1 Lifecycle

```
audio.begin  ──▶ upload_id
binary frames ──▶ (streamed to a temp file on Core, never buffered whole in RAM)
audio.commit ──▶ job_id
```

`audio.begin`:

```json
{"request_id":"01K...","user_id":"tg:123456789","chat_id":123456789,"message_id":4711,
 "filename":"voice.ogg","content_type":"audio/ogg","size":8348293,
 "duration_seconds":612.4,"purpose":"assistant|transcribe_only"}
```

Result `{"upload_id":"01K...","chunk_size":262144,"resume_offset":0}`.

The Core rejects the upload up front with `-32011 audio_too_large` or `-32012 audio_too_long` if
it exceeds `MAX_AUDIO_SIZE_MB` / `MAX_AUDIO_DURATION_SECONDS`, so the Gateway never streams bytes
that are going to be discarded.

`resume_offset` is non-zero when this `request_id` matches a partially received upload that
survived a disconnect, letting the Gateway resume instead of restarting.

### 6.2 Binary frame format

Each binary WebSocket frame is a fixed 32-byte header followed by payload:

```
offset  size  field
0       4     magic         b"PAUP"
4       1     version       1
5       1     flags         bit0 = final chunk
6       2     reserved      zero
8       16    upload_id     ULID, 16 bytes big-endian
24      8     offset        uint64 big-endian, byte offset of this chunk
32      ...   payload
```

A binary `upload_id` avoids a per-frame JSON parse. `offset` makes frames self-describing, so an
out-of-order or duplicated frame is detected rather than silently corrupting the file. The Core
writes at `offset` and tracks received ranges; a frame whose range is already present is
discarded.

Default chunk size 256 KiB.

### 6.3 `audio.commit`

```json
{"upload_id":"01K...","sha256":"<hex>","total_size":8348293}
```

The Core verifies size and digest before accepting. Mismatch → `-32013 upload_incomplete`, the
temp file is deleted, and the Gateway may retry the whole upload. Success returns
`{"job_id":"01K...","status":"accepted"}`.

An upload with no frames for `UPLOAD_IDLE_TIMEOUT` (default 300 s) is garbage-collected and its
temp file deleted. Connection loss mid-upload therefore never leaks disk, and the upload is simply
not acknowledged — the Gateway still holds the file and retries after reconnect.

## 7. Methods — Core → Gateway

The Gateway is a renderer. It receives intent, not Telegram API calls, and it owns all
Telegram-specific encoding — including callback data, which the Core never constructs.

### `telegram.send`

```json
{"delivery_id":"01K...","user_id":"tg:123456789","chat_id":123456789,
 "text":"...","parse_mode":"markdown|plain",
 "reply_to_message_id":4711,"silent":false,"kind":"reply|status|notification"}
```

Result `{"message_id":4712,"dedup":false}`. Text longer than the Telegram limit is split by the
Gateway on paragraph, then line, then hard boundaries; `message_id` is the last part.

### `telegram.send_document`

```json
{"delivery_id":"01K...","user_id":"tg:123456789","chat_id":123456789,
 "filename":"Касперская — конспект.md","content":"# …","mime_type":"text/markdown",
 "caption":"Конспект","parse_mode":"markdown"}
```

A downloadable Telegram document. `content` is UTF-8 text (markdown transcripts and notes);
the Gateway encodes it. Result `{"message_id","dedup"}` with the same at-least-once rule as
`telegram.send`.

### `telegram.edit`
`{"delivery_id","chat_id","message_id","text","parse_mode"}` → `{"edited":true}`. Used to update a
single status message in place instead of spamming progress lines. An edit whose text is unchanged
is skipped (Telegram would reject it).

### `telegram.delete`
`{"delivery_id","chat_id","message_id"}` → `{"deleted":true}`. Deleting an already-deleted message
returns `true`.

### `telegram.action`
`{"chat_id","action":"typing|record_voice|upload_document"}` — notification, no result, never
retried.

### `telegram.confirm`

```json
{"delivery_id":"01K...","action_id":"01K...","user_id":"tg:123456789","chat_id":123456789,
 "text":"Создать встречу завтра с 15:00 до 16:00?",
 "actions":[{"id":"approve","label":"Создать","style":"primary"},
            {"id":"reject","label":"Отмена","style":"secondary"}],
 "expires_at":"2026-08-23T19:10:00+00:00"}
```

The Gateway renders an inline keyboard and maps each button to opaque callback data of its own
design. On press it calls `confirmation.resolve` and never acts on the decision itself. After
`expires_at` the Gateway removes the keyboard and reports `expired` if pressed late.

### `job.progress` (notification)

```json
{"job_id":"01K...","user_id":"tg:123456789","stage":"transcribing","progress":0.43,
 "detail":"12 of 28 minutes"}
```

Stages: `queued`, `downloading`, `transcribing`, `transcribing_cpu`, `summarizing`, `agent`,
`executing_tool`, `waiting_confirmation`, `completed`.

`transcribing_cpu` is the same work as `transcribing` after the GPU host turned out to be
unusable: the Core switched to local CPU whisper, so the remaining wait is much longer.

Progress is advisory and **not durable** — dropping it on a disconnect is correct. The Gateway
coalesces progress into one edited status message per job and rate-limits edits to at most one
every 3 s, because Telegram throttles aggressive editing.

### `job.completed` / `job.failed`

```json
{"job_id":"01K...","user_id":"tg:123456789","result_kind":"text","summary_sent":true}
{"job_id":"01K...","user_id":"tg:123456789","error":{"code":"stt_failed","message":"..."},"retryable":false}
```

These are lifecycle signals for the Gateway's status message. User-visible content is always
delivered through `telegram.send`, never smuggled inside a job event.

## 8. Errors

```json
{"jsonrpc":"2.0","id":"01K...","error":{"code":-32011,"message":"audio_too_large",
 "data":{"limit_mb":500,"actual_mb":812}}}
```

| Code | Name | Retryable |
| --- | --- | --- |
| -32700 / -32600 / -32601 / -32602 | JSON-RPC standard | no |
| -32000 | `protocol_version_unsupported` | no |
| -32001 | `not_ready` | yes, after handshake |
| -32002 | `unauthorized_user` | no |
| -32003 | `rate_limited` | yes, honour `data.retry_after` |
| -32010 | `unknown_upload` | no |
| -32011 | `audio_too_large` | no |
| -32012 | `audio_too_long` | no |
| -32013 | `upload_incomplete` | yes, restart upload |
| -32020 | `job_not_found` | no |
| -32021 | `job_already_finished` | no |
| -32030 | `agent_unavailable` | yes |
| -32031 | `agent_failed` | no |
| -32040 | `stt_unavailable` | yes |
| -32041 | `stt_failed` | no |
| -32050 | `telegram_send_failed` | yes |
| -32051 | `telegram_blocked` | no, drop the delivery |

Error messages are stable machine-readable identifiers; `data` carries the detail. The Gateway
never shows a raw error to the user — it maps codes to Russian text.

## 9. Authorization

Two independent checks, because a compromised Gateway must not become a compromised assistant:

1. **Service identity** — the bearer token proves the peer is the Gateway.
2. **User authorization** — the Core independently checks `user_id` against its own
   `ALLOWED_USERS` allowlist on every request.

The Core never trusts a `user_id` merely because an authenticated Gateway sent it. A Gateway that
has been taken over can still only act as users the Core already permits, and it holds no Cursor
credentials, no memory database and no filesystem access.

## 10. Machine-readable schemas

JSON Schema for every params and result object lives in `docs/schemas/`. Both sides validate
against them in tests, so a drift between this document and the code fails CI rather than
surfacing as a production bug.
